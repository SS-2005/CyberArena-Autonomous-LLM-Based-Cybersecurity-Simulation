1. ADD CONTROLLED PRIVILEGED VM TOOLS
========================================================

Add explicit guest-VM tools such as:

1. install_package
2. restart_service
3. modify_system_config
4. create_user

Design the tool system so additional privileged tools can be added later
without modifying the core Agent loop.

The architecture MUST remain:

Agent
 -> ToolRegistry
 -> VMProvider
 -> VirtualBoxProvider
 -> SSH
 -> assigned VM

The LLM must NEVER directly execute privileged host commands.

The LLM must NEVER receive:
- Windows host credentials
- .env secrets
- VM passwords
- sudo passwords
- SSH private keys
- any secret used internally by the backend

Do NOT implement:
    echo "<password>" | sudo -S ...
Do NOT inject passwords into prompts.
Do NOT expose passwords to the LLM.

The agent should call typed tools instead.


--------------------------------------------------------
1.1 install_package
--------------------------------------------------------

Create a typed tool:

install_package(
    vm_id,
    package_name
)

Requirements:

- Validate package_name before execution.
- Reject empty/invalid package names.
- Do not construct unrestricted shell strings from arbitrary LLM input.
- Execute the package installation inside the assigned VM only.
- Use a controlled privileged mechanism that does NOT require an interactive
  sudo password.
- Return structured output:

{
    vm_id,
    package_name,
    success,
    exit_code,
    stdout,
    stderr,
    duration,
    error
}

The tool must support the normal use case:

Agent:
    execute_command("nmap ...")

VM:
    nmap: command not found

Agent should receive that error.

LLM should then be able to reason:

"nmap is unavailable."

It can call:

    install_package("nmap")

After successful installation it can retry the original command.

Do NOT blindly retry forever.

Maximum tool retry count must be configuration-driven.


--------------------------------------------------------
1.2 restart_service
--------------------------------------------------------

Create:

restart_service(
    vm_id,
    service_name
)

Requirements:

- Validate service_name.
- Execute only inside assigned VM.
- Use controlled passwordless privileged execution.
- Return structured result.
- After restarting, optionally verify service state.
- The verification result must also be returned to the Agent.


--------------------------------------------------------
1.3 modify_system_config
--------------------------------------------------------

Create:

modify_system_config(
    vm_id,
    target,
    operation,
    value
)

Requirements:

- Do NOT implement unrestricted arbitrary root shell execution.
- Introduce an explicit allowlist of supported configuration targets.
- Validate target and operation.
- Keep configuration targets and allowed operations configurable.
- Return before/after or equivalent observable state where practical.
- Return structured success/failure information.

Examples of allowed configuration operations may include:
- changing an allowlisted system configuration file
- enabling/disabling an allowlisted service
- changing an allowlisted configuration key

Do not give the LLM unrestricted root access to modify any file.


--------------------------------------------------------
1.4 create_user
--------------------------------------------------------

Create:

create_user(
    vm_id,
    username,
    groups=[]
)

Requirements:

- Validate username.
- Validate group names against an allowlist/policy.
- Do NOT allow arbitrary privilege escalation through unrestricted group

- Explicitly control whether administrative groups are allowed.
- Return structured result:
    username
    groups
    success
    exit_code
    stdout
    stderr
    error

If an operation would violate the policy, return a normal structured tool
error to the Agent instead of crashing the Agent runtime.

2. PASSWORDLESS PRIVILEGED EXECUTION
========================================================

Implement a secure controlled mechanism so these explicit tools do not
require the interactive sudo password.

Preferred architecture:

Inside each CyberArena Ubuntu VM:

- Create root-owned wrapper commands/scripts for approved privileged
  operations.
- Configure sudoers with narrowly scoped NOPASSWD permissions for those
  wrappers only.
- The wrappers must validate their arguments.
- The SSH user must NOT receive unrestricted NOPASSWD access to arbitrary
  commands.
- The Agent must NOT receive the sudo password.
- The LLM must NOT know how privileged authentication is internally
  implemented.

Example conceptual model:

sudo /usr/local/sbin/cyberarena-install-package <validated-package>
sudo /usr/local/sbin/cyberarena-restart-service <validated-service>

NOT:

sudo bash -c "<arbitrary LLM command>"

and NOT:

echo "$PASSWORD" | sudo -S ...

Use configuration/policy files rather than hardcoding VM-specific values
inside the Agent logic.

If there is already a VM provisioning/setup mechanism, integrate this into
that mechanism.

If not, create a documented provisioning script/setup step for each
CyberArena VM.

The setup MUST be repeatable for VM-01 and VM-02.

4. AGENT ERROR HANDLING
========================================================

This is extremely important.

Currently the agent produced:

    nmap -sn 192.168.32.0/24
    bash: nmap: command not found

then:

    sudo apt update && sudo apt install -y nmap

which failed because sudo required a password.

then the LLM generated:

    echo 'your_password' | sudo -S ...

which was obviously wrong.

THIS BEHAVIOR MUST BE ELIMINATED.

The Agent must NEVER fabricate passwords or placeholders such as:

- your_password
- password
- <password>
- YOUR_PASSWORD

The Agent must understand that credentials are backend-only secrets.

If a privileged operation is needed, it MUST use the explicit privileged
tool.


========================================================
5. TOOL ERROR MUST BE FED BACK TO THE LLM
========================================================

Every tool execution must produce a structured observation available to
the next LLM iteration.

For example:

{
    "tool": "execute_command",
    "success": false,
    "exit_code": 127,
    "stdout": "",
    "stderr": "nmap: command not found",
    "error_type": "command_not_found"
}

The Agent then sends this information back into the LLM context.

The LLM must be able to reason from:

- objective
- previous actions
- tool outputs
- errors
- exit codes
- observations
- retry history
- iteration usage
- VM identity

Do NOT only retain the latest observation.

Maintain an accumulated execution/evidence context for the entire run.


========================================================
6. COMMAND-NOT-FOUND RECOVERY
========================================================

Implement a general recovery pattern.

Example:

Iteration 1:
    execute_command("nmap -sn 192.168.32.0/24")

Result:
    nmap: command not found

LLM interpretation:
    required tool is unavailable

Iteration 2:
    install_package("nmap")

Result:
    installation successful

Iteration 3:
    execute_command("nmap -sn 192.168.32.0/24")

Result:
    actual nmap output

Then continue toward the objective.

Do NOT hardcode "if nmap then install nmap".

The recovery must be generic so the LLM can decide when a missing
dependency should be installed through install_package.

Still enforce:
- package allowlist/policy
- retry limit
- iteration limit
- timeout
- tool availability


========================================================
7. ITERATION LIMIT MUST BE EXPLICITLY INFORMED TO LLM
========================================================

Current problem:

The agent reaches 5/5 iterations and simply reports:

    Agent completed 5 steps.

This is misleading.

When an Agent reaches its iteration limit, the runtime MUST explicitly
inform the LLM that it has reached the configured limit.

However, do NOT perform an additional normal tool-execution iteration after
the limit is exhausted.

Before final conclusion generation, construct a finalization context such as:

EXECUTION LIMIT REACHED

The configured maximum iteration count has been reached.

Agent:
    agent-1

VM:
    vm-01

Iterations:
    5 / 5

The agent must not execute additional tools.

The final conclusion MUST determine whether the objective was:
- completed
- partially completed
- blocked
- failed
- inconclusive

based on the accumulated evidence.

8. FINAL CONCLUSION MUST BE GENERATED BY THE LLM
========================================================

Do NOT generate conclusions like:

    "Agent completed 5 steps on VM vm-01."

That is not a conclusion.

The Agent finalization prompt must contain the accumulated evidence.

Include:

- original objective
- assigned role

- all action summaries
- all tool calls
- all tool results
- stdout/stderr
- exit codes
- errors
- observations
- retries

- iteration limit

- execution status
- unresolved issues

The LLM must produce a concise evidence-based conclusion.

Required conceptual structure:

{
    "status": "completed | partially_completed | blocked | failed | inconclusive",
    "summary": "...",
    "findings": [...],
    "evidence": [...],
    "errors": [...],
    "unresolved_items": [...],
    "iteration_limit_reached": true/false
}



Store/display reasoning summaries and observable evidence.


========================================================
9. FINALIZATION EDGE CASES
========================================================

Handle ALL of these:

A. Objective completed before iteration limit
    -> final LLM conclusion

B. Objective incomplete and iteration limit reached
    -> LLM explicitly told limit was reached
    -> partial/inconclusive conclusion as appropriate

C. Tool returns non-zero exit code
    -> pass error to LLM

D. Tool times out
    -> pass timeout observation to LLM

E. SSH connection fails
    -> pass VM connectivity failure to LLM

F. VM stops/crashes
    -> pass VM state/error to LLM

G. Tool is unavailable
    -> LLM receives tool-unavailable error

H. Privileged tool rejects policy
    -> LLM receives explicit policy rejection

I. Package installation fails
    -> LLM receives installation failure

J. Command produces stderr but exit_code=0
    -> preserve stderr and let LLM interpret it

K. Command produces empty output
    -> preserve that fact

L. Repeated identical failure
    -> avoid infinite repeated attempts

M. LLM suggests password injection
    -> reject/sanitize it and return a tool-policy error

N. LLM suggests arbitrary privileged shell execution
    -> reject it and tell the LLM to use the corresponding privileged tool

O. Agent cancellation
    -> finalize with cancelled status and evidence accumulated so far

P. Backend/LLM generation error during finalization
    -> preserve all execution data
    -> produce a deterministic fallback summary
    -> clearly mark that LLM finalization failed
    -> DO NOT pretend an LLM-generated conclusion exists
